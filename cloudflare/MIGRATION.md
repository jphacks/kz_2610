# 既存クラウドからの切り替え

このブランチは実装を置き換えます。既存Supabaseのプロジェクト・ユーザー・データを削除する処理は含めません。
本番の移送は対象環境とデータの有無を確認したうえで行います。
既存アプリは認証・クラウド同期未接続ですが、旧DBの空状態を仮定して自動切り替えしません。

## データがない場合

管理画面でアプリテーブル・Authユーザー・写真オブジェクトの件数を個別に確認します。
全て空ならCloudflareの新規リソースへmigrationを適用し、[README](README.md)のデプロイ・実アカウント検証を行います。
旧プロジェクトの停止・削除は切り替え検証後の別作業です。

## 既存ユーザーやデータがある場合

1. 旧バックエンドへの書き込みを止め、アクセスを限定した場所にDBと非公開写真のバックアップを取得します。
   エクスポートはGit対象外の`cloudflare/data/`またはリポジトリ外に置きます。ログやチャットにも内容を貼り付けません。
2. 新規D1へ空のスキーマを適用します。PostgresのdumpをそのままD1で実行しません。
3. 本人の対応表を作ります。旧`auth.users.id`を新`users.id`として保持し、検証済みApple identityの`sub`を`auth_subject`へ対応付けます（ハッカソン版のゲストは`guest:<id>`）。
   メール、表示名、推測でアカウントを紐付けません。旧Apple identityがない場合は、旧認証とApple認証の両方を証明する移行フローが別途必要です。
   既存APIは新規Appleユーザーを作るため、対応表を取り込む前に既存ユーザーをログインさせません。
4. アプリデータを型変換します。UUIDと写真キーは保持し、booleanは0/1、日時はUTCのISO 8601文字列、日付はYYYY-MM-DDへ変換します。
   対象はprofiles、profile_preferences、restaurants、reviews、review_visits、review_photos、saved_restaurants、friend_requests、friendships、favorite_friends、blocksです。
5. 通常API経由で過去データを再作成しません。レビューのトリガーは保存状態を変更し、友達のトリガーは現時点の検索設定で過去の申請を拒否し得ます。
   本番取り込み用の一回限りの変換・投入スクリプトで、トリガーの適用順を制御し、外部キーと公開設定を保ちます。
   このブランチには実データ用の投入スクリプトを含めていません。実際の旧データ形式・本人対応方式を確認してから作成します。
6. 旧`review-photos`の各オブジェクトを、同じ`owner/review/photo.jpg`キーで非公開R2へコピーします。
   件数・容量・チェックサムを照合し、公開バケットや公開URLを経由させません。
7. テーブルごとの件数、UUID参照、ユーザー別件数、友達関係、ブロック、来店日非公開設定、写真チェックサムを照合します。
   特に保存一覧の状態とお気に入りが、レビューの取り込みトリガーにより変化していないことを確認します。
8. Cloudflareをデプロイし、移行用のテストアカウントで認証・承認・解除・ブロック・写真アクセス失効を検証します。
   認証セッションは移送しません。既存ユーザーはAppleで再ログインします。
9. iOSのAPI originを変更したビルドを配布します。旧バックエンドは読み取り用バックアップを維持します。

不一致があれば切り替えを止めて旧バックエンドへ戻します。切り戻し後も新側に書かれたデータを保全し、
二重書き込みや片側の書き込み消失を避けて差分を照合します。
